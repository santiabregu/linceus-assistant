\chapter{Estructura del proyecto}\label{cap:estructura-proyecto}

Este capítulo describe la organización del repositorio LinceUS Assistant, detallando el propósito de cada directorio relevante. La estructura ha sido diseñada para separar claramente las responsabilidades entre los distintos módulos del sistema y facilitar el mantenimiento y la escalabilidad del proyecto.

\section{Visión general del repositorio}\label{sec:vision-general}

El repositorio sigue una organización modular en la que cada directorio agrupa elementos con una responsabilidad concreta dentro del sistema. La separación entre la lógica conversacional, los datos de entrenamiento, el pipeline RAG, el panel de administración, la interfaz de usuario y la infraestructura de despliegue responde al principio de separación de responsabilidades (\textit{Separation of Concerns}).

\section{Directorio raíz}\label{sec:directorio-raiz}

Los ficheros situados en la raíz del repositorio configuran el comportamiento global del sistema Rasa y la gestión de dependencias del proyecto:

\begin{itemize}
    \item \texttt{config.yml}: Define el pipeline de procesamiento de lenguaje natural (NLU) y las políticas de diálogo de Rasa, incluidos los nueve componentes descritos en la Sección~\ref{subsec:dd-pipeline}.
    \item \texttt{domain.yml}: Declara el universo del asistente: \textit{intents}, entidades, \textit{slots}, acciones y respuestas predefinidas.
    \item \texttt{credentials.yml}: Configura los canales de comunicación (en este proyecto, REST). Las claves sensibles se gestionan mediante variables de entorno.
    \item \texttt{endpoints.yml}: Configura los endpoints de los servicios externos: \textit{action server}, base de datos y URL del modelo de lenguaje.
    \item \texttt{requirements.txt} y \texttt{requirements-actions.txt}: Dependencias Python del servidor Rasa y del \textit{action server} respectivamente, con versiones ancladas.
    \item \texttt{package.json}: Dependencias de herramientas de desarrollo en JavaScript (ESLint).
\end{itemize}

\section{Directorio \texttt{actions/}}\label{sec:actions}

El directorio \texttt{actions/} contiene la lógica de negocio del asistente, implementada como acciones personalizadas de Rasa. Cuando el motor conversacional determina que debe ejecutar una acción, invoca el código Python correspondiente a través del \textit{action server} (puerto 5055).

\subsection{Organización por épicas}

A diferencia de la versión inicial del prototipo (en la que toda la lógica residía en un único \texttt{actions.py}), el código se organiza en un \textbf{módulo por épica funcional}. Cada subdirectorio (\texttt{asignaturas/}, \texttt{contexto/}, \texttt{fallback/}, \texttt{horarios/}, \texttt{profesores/}) contiene su propio \texttt{actions.py} con las clases que implementan los pipelines descritos en el Capítulo~\ref{cap:implementacion}. El subdirectorio \texttt{asignaturas/} aloja además \texttt{text\_to\_sql.py}, que aísla la generación, sanitización y ejecución de las consultas SQL producidas por Gemini (decisión de diseño en la Sección~\ref{subsec:dd-texttosql}). La épica \texttt{multi\_intent/} permanece como referencia desactivada (Sección~\ref{sec:impl-multi-intent}).

El módulo raíz \texttt{actions/actions.py} actúa como punto de entrada y se limita a re-exportar las clases de cada épica para que Rasa las descubra en un único espacio de nombres.

\subsection{Subdirectorio \texttt{shared/}}

El subdirectorio \texttt{shared/} concentra la complejidad transversal que utilizan varias épicas:

\begin{itemize}
    \item \texttt{db.py}: Cliente de Supabase / PostgreSQL (clase \texttt{DatabaseConnection}, instancia \texttt{db\_client}).
    \item \texttt{gemini\_client.py}: Cliente de Google Gemini, con \textit{timeouts}, reintentos y registro de métricas.
    \item \texttt{ollama\_client.py}: Cliente alternativo de Ollama con la misma interfaz que el de Gemini.
    \item \texttt{matching.py}: \textit{Fuzzy matching} de nombres normalizados (\texttt{rapidfuzz}).
    \item \texttt{follow\_up.py}: Validación centralizada del slot \texttt{contexto\_titulacion} y lógica de seguimiento conversacional.
    \item \texttt{resolver\_afirmacion.py}: Manejo del flujo de afirmación (\textit{``sí, esa''}) sobre la última sugerencia.
    \item \texttt{config.py}: Carga de variables de entorno y diccionario de alias y acrónimos (\texttt{ALIAS\_ASIGNATURAS}, \texttt{TITULACION\_MAP}).
    \item \texttt{logger.py}: Logging estructurado para depuración.
\end{itemize}

\section{Directorio \texttt{admin/}}\label{sec:admin}

El módulo \texttt{admin/} aloja el \textbf{panel de administración}, implementado como una API Flask independiente que se ejecuta en el puerto 5050. Su responsabilidad es ofrecer una interfaz CRUD sobre el dominio académico (centros, titulaciones, asignaturas, profesores, horarios y conversaciones) y orquestar las importaciones desde fuentes externas.

\begin{itemize}
    \item \texttt{app.py}: Punto de entrada Flask. Registra las \textit{blueprints} de \texttt{routes/} y expone \texttt{/health}.
    \item \texttt{routes/}: Un fichero por dominio (\texttt{asignaturas.py}, \texttt{centros.py}, \texttt{titulaciones.py}, \texttt{horarios.py}, \texttt{profesores.py}, \texttt{planes\_docentes.py}, \texttt{conversaciones.py}, \texttt{sevius.py}, \texttt{stats.py}). Cada uno agrupa los endpoints REST de su dominio.
    \item \texttt{db.py}: Helpers de acceso a Supabase específicos del panel (\textit{queries}, ejecución, normalización).
    \item \texttt{sevius\_scraper.py}, \texttt{us\_scraper.py} y \texttt{us\_directorio\_scraper.py}: \textit{Scrapers} del catálogo Sevius y del directorio de profesorado de la Universidad de Sevilla. El scraper auxiliar de directorio se utiliza para resolver correos y despachos cuando el listado principal no los expone.
    \item \texttt{horarios\_extractores/}: Extractores de horarios por centro (clase base más implementación específica, hoy disponible solo para la ETSII).
    \item \texttt{requirements.txt}: Dependencias Python específicas del panel (Flask y librerías auxiliares), separadas del \textit{action server} para reducir el peso de su imagen Docker.
\end{itemize}

\section{Directorio \texttt{rag/}}\label{sec:rag-dir}

El directorio \texttt{rag/} contiene el \textbf{pipeline de Retrieval-Augmented Generation} que vectoriza los planes docentes y soporta la búsqueda semántica. Se ejecuta bajo demanda (no es un servicio permanente) y consume la API de \textit{embeddings} de Gemini.

\begin{itemize}
    \item \texttt{pipeline.py}: Orquestación end-to-end del proceso (extracción $\rightarrow$ chunking $\rightarrow$ embeddings $\rightarrow$ inserción), aplicando el patrón \textit{Pipes and Filters} descrito en el Capítulo~\ref{cap:arquitectura}.
    \item \texttt{extraer\_pdf.py}: Extracción de texto y detección de secciones del plan docente.
    \item \texttt{chunking.py}: Fragmentación con la estrategia definida en la Sección~\ref{subsec:dd-chunking}.
    \item \texttt{embeddings.py}: Generación de vectores con \texttt{gemini-embedding-001} y dimensionalidad reducida.
    \item \texttt{db\_vectores.py}: Persistencia y consulta sobre la tabla \texttt{plan\_docente} con \texttt{pgvector}.
    \item \texttt{buscar.py}: Búsqueda semántica con \textit{fallback} a \texttt{ILIKE} ante agotamiento de cuota.
    \item \texttt{sql/buscar\_plan\_docente.sql}: Función SQL almacenada que encapsula la consulta vectorial.
\end{itemize}

\section{Directorio \texttt{data/}}\label{sec:data}

El directorio \texttt{data/} contiene todos los datos de entrenamiento del modelo Rasa. El subdirectorio \texttt{nlu/} agrupa los \textit{intents} por dominio (\texttt{asignaturas.yml}, \texttt{horarios.yml}, \texttt{profesores.yml}, \texttt{contexto.yml}, \texttt{general.yml}); el fichero \texttt{multi\_intent.yml.disabled} permanece como histórico y, por su extensión, no es cargado por Rasa. \texttt{stories.yml} y \texttt{rules.yml} definen, respectivamente, las historias de entrenamiento del Core y las reglas determinísticas para flujos críticos como el \textit{fallback} o las afirmaciones.

\section{Directorio \texttt{frontend/}}\label{sec:frontend-estructura}

El directorio \texttt{frontend/} contiene tanto el \textbf{widget de chat} como el \textbf{panel de administración}, ambos como aplicaciones HTML/CSS/JS estáticas:

\begin{itemize}
    \item \texttt{chatbot-widget.js}: Widget de chat embebible. Implementa la comunicación con Rasa por HTTP REST, el modal de selección de titulación y el renderizado Markdown.
    \item \texttt{chatbot-icon.html}, \texttt{pagina-principal.html}, \texttt{pagina-principal.css}: Páginas de demostración y prototipo institucional.
    \item \texttt{admin.html}, \texttt{admin.js}, \texttt{admin.css}: Panel SPA que consume la API Flask del módulo \texttt{admin/}.
    \item \texttt{login.html}, \texttt{login.js}: Pantalla de autenticación del panel.
    \item \texttt{nginx.conf} y \texttt{docker-entrypoint.sh}: Configuración del servidor web Nginx para el despliegue en contenedor.
\end{itemize}

\section{Directorio \texttt{docker/}}\label{sec:docker}

El directorio \texttt{docker/} agrupa la infraestructura reproducible de despliegue: \texttt{docker-compose.yml} orquesta los cuatro servicios principales (Rasa, \textit{action server}, API admin y Nginx), y los \texttt{Dockerfile.rasa}, \texttt{Dockerfile.actions} y \texttt{Dockerfile.admin} definen las imágenes correspondientes. Esta separación entre código y empaquetado permite levantar el sistema completo con \texttt{docker compose up} sin instalar dependencias en la máquina anfitriona.

\section{Directorios \texttt{tests/} y \texttt{docs/}}\label{sec:tests-docs}

\texttt{tests/} contiene la suite de pruebas (\texttt{test\_admin.py} con Pytest, \texttt{test\_rag.py}, \texttt{test\_stories.yml} con el formato nativo de Rasa, el \textit{runner} \texttt{run\_test\_plan.py} y los \textit{benchmarks} de \texttt{scripts/}). Los planes y los resultados de las corridas se almacenan en \texttt{plans/} y \texttt{results/} respectivamente, y se referencian individualmente en el Capítulo~\ref{cap:pruebas}.

\texttt{docs/} agrupa la documentación técnica generada durante el desarrollo: documentación por sprint, diccionarios del sistema, notas de diseño y planes de implementación. \texttt{knowledge\_base/} aloja los planes docentes en PDF que el \textit{pipeline} RAG vectoriza. \texttt{models/} guarda los modelos entrenados de Rasa, y \texttt{memoria\_tfg/} contiene la presente memoria en LaTeX y los entregables asociados.

\section{Separación de responsabilidades}\label{sec:separacion-responsabilidades}

La estructura del repositorio refleja una separación clara entre los distintos módulos del sistema:

\begin{itemize}
    \item \textbf{Mantenibilidad}: Cada módulo puede modificarse de forma independiente sin afectar al resto del sistema, siempre que se respete la interfaz entre capas.
    \item \textbf{Testabilidad}: Los módulos de acceso a datos y de clientes de IA pueden probarse de forma aislada mediante \textit{mocks}, como demuestra la suite \texttt{test\_admin.py} (Capítulo~\ref{cap:pruebas}).
    \item \textbf{Escalabilidad}: Añadir soporte para nuevas épicas (por ejemplo, ampliar el dominio a otros centros de la Universidad de Sevilla) implica crear un nuevo subdirectorio en \texttt{actions/} y ampliar los datos en \texttt{data/nlu/}, sin modificar la arquitectura existente.
    \item \textbf{Reproducibilidad}: La combinación de Docker, ficheros de \textit{requirements} con versiones ancladas y separación entre código y configuración permite que cualquier desarrollador reconstruya el entorno completo con un único comando.
\end{itemize}
