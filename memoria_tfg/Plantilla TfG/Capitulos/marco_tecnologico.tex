\chapter{Marco tecnológico}\label{cap:marco-tecnologico}

Este capítulo describe el conjunto de tecnologías, frameworks y paradigmas que conforman la base técnica del proyecto LinceUS Assistant. Se complementa con el Capítulo~\ref{cap:arquitectura}, donde se detallan la arquitectura del sistema, las decisiones de diseño y los diagramas de componentes y despliegue, y con la Sección~\ref{subsubsec:investigacion} del Capítulo~\ref{cap:planificacion}, que recoge la comparativa cuantitativa de \textit{frameworks} (Rasa, Botpress, DeepPavlov), motores de LLM (Gemini, OpenAI, DeepSeek, Ollama) y bases vectoriales que sustenta las decisiones aquí adoptadas. Para evitar duplicación, este capítulo describe el rol de cada tecnología en el sistema sin reabrir la justificación cuantitativa.

\section{Tecnologías de procesamiento conversacional}\label{sec:procesamiento-conversacional}

\subsection{Rasa Framework}

Rasa~\cite{rasadocs,bocklisch2017rasa} es el \textit{framework} de código abierto sobre el que se construye el núcleo conversacional del asistente. La justificación cuantitativa de su elección frente a Botpress y DeepPavlov (coste, integración con Python, soporte de RAG y despliegue local) figura en la tarea 1.2.2 del Diccionario EDT (Capítulo~\ref{cap:planificacion}).

\subsubsection{Componentes de Rasa utilizados}

\textbf{Rasa NLU (Natural Language Understanding)}

Rasa NLU se encarga de interpretar la entrada del usuario y extraer:
\begin{itemize}
    \item \textbf{Intenciones (intents)}: ¿Qué quiere hacer el usuario? (e.g., \texttt{consultar\_horario}, \texttt{buscar\_asignatura})
    \item \textbf{Entidades (entities)}: Información específica mencionada por el usuario (e.g., nombre de asignatura, curso, centro)
\end{itemize}

\textbf{Rasa Core}

Rasa Core gestiona el flujo de conversación mediante:
\begin{itemize}
    \item \textbf{Stories}: Conversaciones de ejemplo que entrenan el modelo de diálogo
    \item \textbf{Rules}: Reglas determinísticas para situaciones específicas
    \item \textbf{Políticas}: Algoritmos de aprendizaje que deciden la siguiente acción del bot
\end{itemize}

\textbf{Rasa Actions}

Las acciones personalizadas permiten al bot ejecutar código Python para:
\begin{itemize}
    \item Consultar la base de datos
    \item Generar respuestas dinámicas
    \item Llamar a APIs externas
    \item Procesar lógica de negocio compleja
\end{itemize}

\subsection{Procesamiento de Lenguaje Natural}

\subsubsection{spaCy}

spaCy proporciona capacidades avanzadas de NLP en español:

\begin{itemize}
    \item \textbf{Tokenización}: Separación del texto en palabras y signos de puntuación
    \item \textbf{Lematización}: Reducción de palabras a su forma base
    \item \textbf{Análisis morfológico}: Identificación de categorías gramaticales
    \item \textbf{Vectores de palabras}: Representaciones numéricas del significado de las palabras
\end{itemize}

El modelo \texttt{es\_core\_news\_md} incluye vocabulario específico del español y ha sido entrenado en corpus de textos en español.

\subsubsection{Coincidencia difusa (Fuzzy Matching)}

La librería RapidFuzz implementa algoritmos de distancia de cadenas que permiten:

\begin{itemize}
    \item Tolerar errores ortográficos (e.g., "Fundamnetos de Programacion")
    \item Reconocer abreviaturas (e.g., "FP" por "Fundamentos de Programación")
    \item Manejar variaciones en la escritura (e.g., mayúsculas, tildes)
\end{itemize}

Se utiliza el algoritmo de \textit{Levenshtein distance} con un umbral de similitud del 80\% para considerar coincidencias válidas.

\section{Tecnologías de Inteligencia Artificial}\label{sec:ia}

\subsection{Google Gemini como modelo de lenguaje principal}

El modelo de lenguaje de referencia del sistema es \textbf{Google Gemini}~\cite{geminidocs}, en concreto la familia \texttt{gemma-3-27b-it} para generación de texto y \texttt{gemini-embedding-001} para vectorización. Las llamadas al modelo se centralizan en el cliente \texttt{actions/shared/gemini\_client.py}, que envuelve el SDK oficial y aplica los parámetros de proyecto (temperatura, \textit{timeout}, registro de métricas). La selección de Gemini frente al resto de candidatos analizados se justifica de manera cuantitativa en la comparativa de la Sección~\ref{subsubsec:investigacion}.

Gemini interviene en tres puntos del sistema:

\begin{enumerate}
    \item \textbf{Text-to-SQL}: a partir del esquema de la base de datos y la pregunta del usuario, el modelo genera la sentencia \texttt{SELECT} que se ejecuta tras pasar por un validador propio.
    \item \textbf{Generación de respuesta natural}: tanto los datos estructurados recuperados de la base relacional como los \textit{chunks} devueltos por el módulo RAG se entregan al modelo junto con un \textit{prompt} específico de cada épica para producir la respuesta final.
    \item \textbf{Embeddings}: la vectorización de los planes docentes y de las consultas de búsqueda usa \texttt{gemini-embedding-001} con dimensionalidad reducida a 2000 (decisión documentada en la Sección~\ref{subsec:dd-embeddings}).
\end{enumerate}

\subsection{Ollama como alternativa local opcional}

\textbf{Ollama} se mantiene como motor de inferencia local opcional y se utilizó principalmente durante la fase de prototipado, antes de adoptar Gemini como proveedor estable. En el despliegue actual no es un servicio en ejecución sino una vía alternativa que el cliente \texttt{actions/shared/ollama\_client.py} expone con la misma interfaz que el cliente de Gemini. Esto permite, sin reescribir el núcleo conversacional:

\begin{itemize}
    \item Probar localmente nuevos \textit{prompts} sin consumir cuota de la API de Gemini.
    \item Disponer de un \textit{plan B} ante cambios de política o cuotas del proveedor cloud (precedente histórico recogido en la Sección~\ref{sec:costes}).
    \item Ejecutar el sistema en entornos sin conectividad a servicios externos.
\end{itemize}

\subsection{Embeddings y búsqueda semántica (RAG)}

La recuperación de información sobre los planes docentes oficiales se implementa mediante el patrón \textit{Retrieval-Augmented Generation}~\cite{lewis2020retrieval}, que combina búsqueda semántica y generación con LLM. Las piezas son:

\begin{itemize}
    \item \textbf{Modelo de embeddings} (\texttt{gemini-embedding-001}): transforma texto en vectores que capturan el significado semántico.
    \item \textbf{pgvector}~\cite{pgvectorgithub}: extensión de PostgreSQL que almacena los vectores y soporta búsqueda por similitud coseno.
    \item \textbf{Índice HNSW}~\cite{malkov2018hnsw}: estructura de vecinos más cercanos aproximados que ofrece tiempos de consulta sub-lineales sobre el corpus de planes docentes.
\end{itemize}

Las decisiones concretas de \textit{chunking} (800 caracteres con 100 de solapamiento) y dimensionalidad (2000) se documentan en las Secciones~\ref{subsec:dd-chunking} y~\ref{subsec:dd-embeddings} respectivamente.

\section{Tecnologías de base de datos}\label{sec:base-datos}

La capa de datos se apoya en PostgreSQL como motor relacional, Supabase~\cite{supabasedocs} como plataforma gestionada y pgvector~\cite{pgvectorgithub} como extensión vectorial. La elección frente a alternativas (Pinecone, Weaviate~\cite{weaviatedocs}, Qdrant~\cite{qdrantdocs}) se discute en la fase de investigación recogida en el Diccionario EDT (Sección~\ref{subsubsec:investigacion}); aquí basta con detallar el rol de cada pieza en el sistema.

\subsection{PostgreSQL y Supabase}

\textbf{PostgreSQL} almacena toda la información académica estructurada (universidades, centros, titulaciones, asignaturas, planes docentes, profesorado, horarios). \textbf{Supabase} actúa como capa gestionada: ofrece la instancia de PostgreSQL en \textit{cloud}, el \textit{connection pooling} a través del puerto 6543, autenticación, almacenamiento de ficheros y panel de administración. El proyecto utiliza Supabase exclusivamente como base de datos gestionada; las API REST y \textit{Edge Functions} no se emplean porque toda la lógica reside en las acciones de Rasa y en la API Flask del panel de administración.

\subsection{pgvector}

La extensión \textbf{pgvector}~\cite{pgvectorgithub} añade el tipo \texttt{vector} y los operadores de similitud (coseno, euclidiana, producto punto) directamente sobre PostgreSQL. Esto evita introducir un servicio adicional de base vectorial: el corpus de planes docentes y sus embeddings residen en la misma instancia que el resto de datos académicos. Sobre los vectores se construye un índice HNSW~\cite{malkov2018hnsw} para búsquedas sub-lineales, configurado con los parámetros $m=16$ y $ef\_construction=64$ (Sección~\ref{subsec:dd-embeddings}).

\section{Tecnologías de frontend}\label{sec:frontend}

El frontend del proyecto está formado por dos piezas: el \textbf{widget de chat} embebible en cualquier página de la US y el \textbf{panel de administración} que da acceso a las importaciones de datos y a las conversaciones registradas. Ambas son aplicaciones estáticas (HTML, CSS y JavaScript ES6+ sin \textit{frameworks} reactivos) servidas por Nginx en producción y por el servidor HTTP de Python en desarrollo. La separación entre el widget del usuario, el panel de administración, el servidor conversacional y el servidor de acciones sigue los principios de desacoplamiento propios de las arquitecturas de microservicios~\cite{newman2021microservices}.

\subsection{Widget de chat}

El \texttt{chatbot-widget.js} se carga directamente desde una página HTML mediante una etiqueta \texttt{<script>}, sin pasos de \textit{build}. Implementa:

\begin{itemize}
    \item La comunicación con el servidor Rasa por HTTP REST contra el endpoint \texttt{/\allowbreak webhooks/\allowbreak rest/\allowbreak webhook} (peticiones síncronas \texttt{fetch}, sin WebSocket).
    \item El renderizado de respuestas en Markdown ligero (tablas, listas, enlaces, énfasis) y de botones inyectados desde Rasa.
    \item El \textbf{modal de selección de titulación} que se muestra al iniciar la sesión y fija el slot \texttt{contexto\_titulacion} antes de la primera consulta (Sección~\ref{subsec:dd-slots}).
\end{itemize}

\subsection{Panel de administración}

El panel (\texttt{admin.html}, \texttt{admin.js}, \texttt{admin.css}) es una aplicación SPA ligera que consume la API Flask descrita en la Sección~\ref{sec:procesamiento-conversacional}. Permite gestionar centros, titulaciones, asignaturas, profesores, horarios y conversaciones, y dispara las importaciones desde Sevius mediante los \textit{scrapers} del módulo \texttt{admin/}.

\subsection{Servidor web}

\textbf{Nginx} sirve los activos estáticos del \textit{frontend} y el panel en el despliegue Docker (puerto 80) y actúa como \textit{reverse proxy} hacia los servicios internos. En desarrollo local, los mismos activos se sirven con \texttt{python -m http.server 8080}. Node.js se utiliza únicamente para herramientas de desarrollo (ESLint~\cite{eslint} a través de \texttt{npm}); ningún componente del \textit{runtime} depende de él.

\section{Herramientas de desarrollo}\label{sec:herramientas-desarrollo-marco}

\subsection{Control de versiones}

\textbf{Git} es el sistema de control de versiones utilizado, con \textbf{GitHub} como plataforma de \textit{hosting}. La estructura concreta del repositorio se detalla en el Capítulo~\ref{cap:estructura-proyecto}; no se reproduce aquí para evitar duplicar información.

\subsection{Gestión de dependencias}

Las dependencias de Python se fijan en \texttt{requirements.txt} (servidor Rasa) y \texttt{requirements-actions.txt} (\textit{action server}), ambos con versiones ancladas para garantizar la reproducibilidad. El aislamiento del entorno se consigue con \textit{venv} en desarrollo y con la imagen Docker en producción.

\subsection{Variables de entorno}

La librería \texttt{python-dotenv} carga la configuración desde un fichero \texttt{.env} en la raíz del proyecto: credenciales de Supabase (URL y API key), clave de la API de Gemini, parámetros opcionales de Ollama y el resto de ajustes del sistema. Este mecanismo evita exponer secretos en el repositorio y permite alternar entre entornos (local, Docker, producción) sin tocar el código.

\section{Consideraciones de seguridad}\label{sec:seguridad}

\subsection{Protección de datos}

\begin{itemize}
    \item \textbf{Credenciales}: Nunca se almacenan en el código, siempre en variables de entorno
    \item \textbf{API keys}: Se utilizan claves específicas con permisos mínimos necesarios
    \item \textbf{Conexiones}: HTTPS para todas las comunicaciones con servicios externos
\end{itemize}

\subsection{Validación de entrada}

\begin{itemize}
    \item Sanitización de consultas SQL para prevenir inyección SQL
    \item Validación de tipos de datos en entradas de usuario
    \item Limitación de longitud de mensajes
\end{itemize}

\subsection{Aislamiento del proveedor de LLM}

En el despliegue actual, las consultas se envían a la API de Google Gemini~\cite{geminidocs} sobre HTTPS y autenticación por clave; no se transmiten datos personales del alumnado, sino exclusivamente el texto de la consulta y, cuando aplica, los \textit{chunks} recuperados de los planes docentes (que son documentos públicos). El cliente \texttt{shared/gemini\_client.py} centraliza estas llamadas, lo que aporta dos garantías relevantes desde el punto de vista de seguridad y privacidad:

\begin{itemize}
    \item \textbf{Punto único de auditoría}: cualquier llamada saliente al LLM atraviesa el cliente, lo que facilita la inspección de \textit{prompts}, el registro de uso y la aplicación de filtros si fuera necesario.
    \item \textbf{Sustituibilidad del proveedor}: el cliente \texttt{shared/ollama\_client.py} implementa la misma interfaz, de modo que ante un cambio de política de Google o un escenario que exija inferencia local (por ejemplo, un despliegue institucional sobre infraestructura propia de la US, ver Sección~\ref{sec:costes}), se puede conmutar a Ollama sin tocar las acciones de Rasa.
\end{itemize}

La opción local con Ollama se mantiene, por tanto, como mecanismo de mitigación de riesgo (cambios de cuotas o términos de uso del proveedor cloud) y no como modo de operación por defecto.

\paragraph{Nota sobre el modelo \texttt{gemma-3-27b-it}.} El modelo \texttt{gemma-3-27b-it} es el que se utilizó durante toda la fase de desarrollo y validación del prototipo, y por tanto el que sustenta las métricas reportadas en el Capítulo~\ref{cap:pruebas} (latencia mediana 3,4~s, coste medio por turno 0,012~céntimos, 216~llamadas medidas). Tras el cierre del prototipo, Google retiró ese modelo de su catálogo público en mayo de 2026 y lo sustituyó por la familia \texttt{Gemma~4}. Para mantener operativo el sistema sin reescribir su pipeline, la constante \texttt{GEMINI\_MODEL} del cliente (\texttt{actions/shared/gemini\_client.py}) se actualizó al sucesor más directo dentro de la misma familia, \texttt{gemma-4-26b-a4b-it} (arquitectura \textit{Mixture-of-Experts}, $\sim$26\,B parámetros activos). Las métricas medidas durante el TFG no se han reproducido sobre el nuevo modelo: dado el carácter conmutable del cliente LLM (Sección~\ref{subsec:dd-gemini-ollama}), cualquier revalidación posterior bastaría con relanzar la suite del Capítulo~\ref{cap:pruebas} sin tocar el resto del sistema.
